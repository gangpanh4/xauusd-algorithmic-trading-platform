# Market Event Specification

**Document ID:** SMC-SPEC-011

**Version:** 1.0

**Status:** Draft

**Project:** Trading Intelligence Platform

**Module:** Market Structure Engine

---

# 1. Purpose

The Market Event Specification defines the common representation of immutable market events generated by the Market Structure Engine.

A Market Event represents a confirmed structural occurrence detected during market analysis.

Market Events provide a standardized interface for communication between detectors and downstream analytical components.

This specification establishes the shared data model, ownership rules, lifecycle, and behavioral contract for every event generated within the Market Structure Engine.

Market Events provide a common interface for:

- Swing Events
- BOS Events
- CHOCH Events
- Liquidity Events
- Order Block Events
- Fair Value Gap Events
- Breaker Block Events
- Mitigation Events

The specification does not define detector-specific algorithms.

Detection logic remains the responsibility of the owning detector.

---

# 2. Scope

This specification defines the common behavior shared by every Market Event.

It SHALL define:

- Event ownership
- Event identifiers
- Event timestamps
- Event metadata
- Event references
- Immutability rules
- Common interfaces

It SHALL NOT define:

- Swing algorithms
- BOS algorithms
- CHOCH algorithms
- Liquidity algorithms
- Order Block algorithms
- Fair Value Gap algorithms
- Breaker algorithms
- Mitigation algorithms

These remain detector-specific responsibilities.

---

# 3. Owner

Every Market Event shall have exactly one owning detector.

Examples include:

| Event Type | Owner |
|------------|-------|
| SwingEvent | Swing Detector |
| BOSEvent | BOS Detector |
| CHOCHEvent | CHOCH Detector |
| LiquidityEvent | Liquidity Detector |
| OrderBlockEvent | Order Block Detector |
| FairValueGapEvent | Fair Value Gap Detector |
| BreakerBlockEvent | Breaker Block Detector |
| MitigationEvent | Mitigation Block Detector |

Ownership shall never transfer.

No detector may modify an event owned by another detector.

---

# 4. Responsibilities

A Market Event represents a confirmed historical fact.

Every Market Event shall:

- Be immutable after creation.
- Have a globally unique identifier.
- Record creation time.
- Reference originating market data.
- Reference related structural objects.
- Support deterministic replay.
- Support serialization.
- Support historical analysis.

Market Events shall never generate trading signals.

---

# 5. Common Properties

Every Market Event shall expose the following immutable properties.

| Property | Description |
|----------|-------------|
| Event ID | Globally unique identifier |
| Event Type | Swing, BOS, CHOCH, etc. |
| Source Detector | Detector that created the event |
| Timestamp | Event timestamp |
| Confirmation Timestamp | Confirmation time |
| Direction | Bullish, Bearish, Neutral |
| Version | Event schema version |

These properties shall never change after event creation.

# 9. Event Lifecycle

Every Market Event shall follow a deterministic lifecycle.

Unlike Price Zones, Market Events represent immutable historical facts.

Once confirmed, an event shall never be modified.

```text
Detected
    │
    ▼
Validated
    │
    ▼
Confirmed
    │
    ▼
Recorded
```

After reaching the Recorded state, the event becomes permanently immutable.

Historical replay shall always reproduce the same event lifecycle.

---

## 9.1 Detected

An event enters the Detected state when the owning detector identifies a candidate structural occurrence.

At this stage:

- Validation has not completed.
- The event is internal to the detector.
- No downstream component may consume the event.

Detected events are temporary runtime objects.

---

## 9.2 Validated

The detector validates the candidate event using detector-specific rules.

Validation may include:

- Structural confirmation
- Price confirmation
- Configuration checks
- Duplicate detection
- ATR validation
- Trend validation

Validation rules are owned entirely by the detector.

The Market Event abstraction does not define validation algorithms.

---

## 9.3 Confirmed

A Market Event becomes Confirmed only after all detector-specific validation succeeds.

Upon confirmation:

- A globally unique Event ID shall be assigned.
- Confirmation Timestamp shall be recorded.
- Immutable properties shall be finalized.

From this point onward, the event shall never be modified.

---

## 9.4 Recorded

Confirmed events enter the Recorded state.

Recorded events become part of the permanent historical event stream.

Recorded events may be:

- Serialized
- Stored
- Replayed
- Referenced
- Analyzed

Recorded events shall never be deleted during normal processing.

---

# 10. State Management

Market Events are immutable.

The Market Event abstraction maintains no mutable runtime state after confirmation.

Mutable processing state exists only inside the owning detector before confirmation.

After confirmation, the event shall expose only immutable data.

---

## Runtime Processing

The owning detector may maintain temporary processing state while evaluating candidate events.

Examples include:

- Candidate Swing
- Candidate BOS
- Candidate CHOCH
- Candidate Liquidity Event

Candidate objects shall never be exposed outside the detector.

Only confirmed Market Events become part of the public event stream.

---

## Reset Behavior

Reset operations shall:

- Clear detector runtime state.
- Remove unconfirmed candidate events.
- Preserve deterministic replay behavior.

Confirmed historical events shall be reproducible after reset.

---

# 11. Ownership Rules

Each Market Event has exactly one owner.

Ownership shall never transfer.

The owning detector is solely responsible for:

- Event creation
- Validation
- Confirmation
- Event publication

After publication:

- No detector may modify the event.
- No detector may delete the event.
- No detector may reassign ownership.

Other detectors may consume events but shall treat them as read-only.

---

## Ownership Matrix

| Event Type | Owner |
|------------|-------|
| SwingEvent | Swing Detector |
| BOSEvent | BOS Detector |
| CHOCHEvent | CHOCH Detector |
| LiquidityEvent | Liquidity Detector |
| OrderBlockEvent | Order Block Detector |
| FairValueGapEvent | Fair Value Gap Detector |
| BreakerBlockEvent | Breaker Block Detector |
| MitigationEvent | Mitigation Block Detector |

Each detector owns only the events it produces.

---

# 12. Event Relationships

Market Events may reference previously confirmed events.

Examples include:

- BOSEvent → SwingEvent
- CHOCHEvent → BOSEvent
- LiquidityEvent → SwingEvent
- OrderBlockEvent → BOSEvent
- FairValueGapEvent → BOSEvent
- BreakerBlockEvent → OrderBlockEvent
- MitigationEvent → PriceZone

Relationships shall use immutable identifiers.

Referenced events shall never be embedded or duplicated.

This preserves a normalized event graph and avoids redundant historical data.

---

# 13. Deterministic Guarantees

The Market Event abstraction shall satisfy the following guarantees.

## Historical Replay

Identical historical market data shall always produce identical Market Events.

---

## Immutable Events

After confirmation, the following properties shall never change:

- Event ID
- Event Type
- Timestamp
- Confirmation Timestamp
- Source Detector
- References
- Measurements
- Metadata

---

## Sequential Processing

Completed MarketBars shall be processed strictly in chronological order.

Events shall be emitted in the exact order they are confirmed.

---

## Non-Repainting

Confirmed Market Events shall never be modified, removed, or replaced.

If new structural information becomes available, a new Market Event shall be emitted instead of altering an existing event.

---

## Idempotent Processing

Processing identical historical data multiple times shall always produce:

- Identical Market Events
- Identical Event IDs (if deterministic ID generation is used)
- Identical Event Ordering
- Identical References
- Identical Measurements

No detector shall modify Market Events owned by another detector.

---

---

# 14. Measurements

Every Market Event shall expose quantitative measurements describing the confirmed structural occurrence.

Measurements provide standardized inputs for:

- Feature Engineering
- Research Analytics
- Probability Engine
- Visualization

The Market Event abstraction shall not perform signal generation or trading decisions.

---

## 14.1 Event Metadata

Every Market Event shall expose:

- Event ID
- Event Type
- Source Detector
- Event Timestamp
- Confirmation Timestamp
- Event Direction
- Event Version

These values uniquely identify the event and provide historical traceability.

---

## 14.2 Structural References

A Market Event may reference one or more structural objects using immutable identifiers.

Possible references include:

- MarketBar ID
- SwingEvent ID
- BOSEvent ID
- CHOCHEvent ID
- LiquidityStructure ID
- OrderBlockZone ID
- FairValueGapZone ID
- BreakerBlockZone ID
- PriceZone ID

References shall never be modified after confirmation.

---

## 14.3 Event Measurements

The owning detector may expose detector-specific measurements.

Examples include:

- BOS Break Distance
- CHOCH Reversal Strength
- Liquidity Sweep Depth
- Order Block Strength
- Fair Value Gap Size
- Breaker Confirmation Strength
- Mitigation Depth

The Market Event abstraction does not define measurement algorithms.

---

## 14.4 Quality Measurements

The owning detector may compute quality metrics describing the confidence or strength of the confirmed event.

Examples include:

- Confidence Score
- Strength Score
- Quality Score
- Structural Significance

Quality calculations remain detector-specific.

---

Required properties include:

- Event Identifier

- Confirmation Timestamp
- Direction
- References
- Measurements

Required behaviors include:

- Retrieve metadata
- Retrieve references
- Retrieve measurements

The Market Event abstraction shall not expose mutable operations.

---

# 16. Failure Cases

The Market Event abstraction shall safely handle the following conditions.

## Invalid Event Identifier

If a unique Event ID cannot be assigned:

- Event confirmation shall fail.

---

## Invalid Timestamp

If the event timestamp is invalid:

- Event confirmation shall fail.

---

## Missing Required Reference

If a required structural reference cannot be resolved:

- The event shall not be confirmed.

Optional references may remain unset.

---

## Duplicate Event

If an equivalent confirmed event already exists:

- The duplicate shall be rejected by the owning detector.

---

## Historical Replay

Historical replay shall always reproduce identical Market Events.

---

## Reset

Reset operations shall remove temporary candidate events while preserving deterministic replay behavior.

---

The Market Event abstraction shall satisfy the following requirements.

## Processing

- Streaming compatible
- Low-overhead serialization

---

## Memory

- Metadata

- Identical Market Events

The abstraction shall support:
